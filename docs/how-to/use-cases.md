# ユースケースガイド

## 選択表

| 判断基準 | ケース1: 簡易試作 | ケース2: HCD可視化 | ケース3: 調査から開始 |
| --- | --- | --- | --- |
| 主目的 | 早く動くものを見る | 適切な可視化方法を検討する | 誰の何を解くかから決める |
| 既知の情報 | データと見たい内容が明確 | ユーザーと課題は概ね明確 | ユーザー・課題も未確定 |
| 期間目安 | 数時間〜数日 | 数日〜数週間 | 数週間〜 |
| 主な成果物 | Streamlitアプリ | 可視化仕様、プロトタイプ、評価 | 調査結果、ペルソナ、要求、試作 |
| 最初のプロンプト | `/analyze-data` | `/hcd-discovery` | `/research-plan` |

## ケース1: Streamlitで簡易的にデータ分析・可視化する

### 適している状況

- データがすでにある
- 確認したい問いが明確
- まず関係者と動くものを見ながら話したい
- 本番品質より学習速度を優先する

### 推奨フロー

1. `/analyze-data`
2. `/prototype-streamlit`
3. `/write-tests`
4. `/review-code`

### 入力例

```text
/analyze-data data/sales.csvを使い、地域ごとの月次売上の変化と急増・急減を確認したい。
利用者は営業企画担当者。まずデータ品質と適切な指標・グラフを整理してほしい。
```

```text
/prototype-streamlit 分析結果をもとに、地域と期間を選べる簡易アプリを作成してほしい。
初期表示、データなし、読込失敗の状態も用意する。
```

### 完了条件

- 問いに対応した指標とグラフがある
- 集計・除外条件が説明されている
- データなし・異常・エラーが扱われている
- 変換ロジックにテストがある
- 起動方法が文書化されている

### ケース2へ移る目安

- 意思決定に利用される
- 複数のユーザー層がいる
- 誤読による影響が大きい
- 表現方法や操作方法に複数の候補がある

## ケース2: HCDに準拠して可視化と方法を検討する

### 適している状況

- 対象ユーザーと課題は概ね分かっている
- グラフの種類だけでなく、情報の順序や操作方法も検討したい
- 実利用環境での評価を行いたい

### 推奨フロー

1. `/hcd-discovery`
2. `/define-jtbd`または`/map-user-journey`
3. `/define-requirements`
4. `/design-visualization`
5. `/prototype-ui`
6. `/usability-test-plan`
7. `/usability-review`
8. `/accessibility-review`
9. `/implement-change`

### 入力例

```text
/hcd-discovery 店舗責任者が混雑状況を見て人員配置を判断するダッシュボードを検討している。
現在分かっているユーザー、利用場面、意思決定、仮定、追加調査事項を整理してほしい。
```

```text
/design-visualization 店舗責任者が「今どこへ人を移すべきか」を短時間で判断できる可視化を設計したい。
時間帯別人数、エリア密度、移動傾向がある。候補を比較して仕様書を作成してほしい。
```

### 完了条件

- ユーザー、利用状況、判断内容が明文化されている
- 可視化の選定理由と却下案が残っている
- 要求から画面まで追跡できる
- 代表タスクで評価されている
- アクセシビリティ上の重大な障壁が解消されている

## ケース3: アンケートやペルソナ定義から実施する

### 適している状況

- 誰のどの課題を解くかが十分に分かっていない
- 関係者の仮説をユーザー調査で検証したい
- セグメント、ペルソナ、要求を根拠付きで作りたい

### 推奨フロー

1. `/research-plan`
2. `/design-survey`
3. 調査実施
4. `/analyze-survey`
5. `/create-persona`
6. `/define-jtbd`
7. `/map-user-journey`
8. `/define-requirements`
9. ケース2の設計・評価フローへ移行

### 重要な順序

ペルソナを先に作るのではなく、原則として次の順に進めます。

```text
調査計画 → 調査票 → データ収集 → 分析 → セグメント → ペルソナ → 要求
```

調査前に作る場合は「仮説ペルソナ」または「プロトペルソナ」と明記し、検証項目を残します。

### 入力例

```text
/research-plan ボードゲーム中の各プレイヤーの思考時間を可視化するサービスを検討している。
ユーザーが記録を負担に感じず、プレイ中・終了後に何を知りたいかを調べたい。
対象者、方法、質問、分析方法を含む調査計画を作成してほしい。
```

### 完了条件

- 調査目的が実際の設計判断と結び付いている
- 質問と分析方法が対応している
- サンプルの偏りと限界が記録されている
- ペルソナの各特徴が証拠へ追跡できる
- 要求に受け入れ条件がある
