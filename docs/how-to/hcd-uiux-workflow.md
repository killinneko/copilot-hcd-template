# HCD・UI/UXワークフロー

## 全体像

```text
計画
  ↓
利用状況の理解
  ↓
ユーザー要求の明確化
  ↓
設計案の作成
  ↓
要求に対する評価
  ↺ 必要に応じて反復
```

## 1. 計画

目的、意思決定、対象、期間、役割、方法、成果物、倫理・個人情報上の制約を決めます。

推奨プロンプト:

- `/hcd-discovery`
- `/research-plan`

成果物:

- `research-plan.md`
- `project-context.md`

## 2. 利用状況の理解

ユーザー、目標、タスク、環境、道具、制約、現在の行動を把握します。アンケートだけでなく、インタビュー、観察、ログ分析など、問いに合う方法を選びます。

推奨プロンプト:

- `/design-survey`
- `/analyze-survey`
- `/map-user-journey`

確認事項:

- 観察事実と解釈が分離されているか
- 参加者選定とサンプルの偏りを説明できるか
- 個人情報と同意の扱いが明確か

## 3. ユーザー要求の明確化

調査結果から、ユーザーが達成すべきことと品質条件を定義します。

推奨プロンプト:

- `/create-persona`
- `/define-jtbd`
- `/define-requirements`

要求には、ID、根拠、優先度、受け入れ条件を持たせます。解決策を早期に固定しないよう、「画面にグラフを置く」ではなく「変化を30秒以内に判別できる」のような成果基準も検討します。

## 4. 設計案の作成

タスクフロー、情報構造、可視化、画面、状態、コンテンツを設計します。

推奨プロンプト:

- `/design-information-architecture`
- `/design-visualization`
- `/prototype-ui`
- `/prototype-streamlit`

設計では通常状態だけでなく、読込中、空、エラー、権限不足、部分成功、完了、取消、復旧を扱います。

## 5. 評価

要求と代表タスクに照らして、ユーザビリティとアクセシビリティを確認します。

推奨プロンプト:

- `/usability-test-plan`
- `/usability-review`
- `/accessibility-review`
- `/release-readiness`

専門家レビューとユーザーテストは代替関係ではありません。専門家レビューで明らかな問題を減らし、代表ユーザーによる評価で実際の理解・行動・困難を確認します。

## 記録の原則

各判断を次の順で追跡できるようにします。

```text
証拠 → 解釈 → ユーザーニーズ → 要求 → 設計 → 評価結果 → 改善
```

確度が不足する項目は、事実のように扱わず「仮定」「仮説」「未検証」と明記します。
